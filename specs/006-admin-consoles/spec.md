# Feature Specification: 관리 화면 (시스템 관리자 콘솔과 블로그 관리)

**Feature Branch**: `006-admin-consoles`

**Created**: 2026-10-06

**Status**: Draft

**Input**: User description: "전체 시스템 관리자의 관리자 페이지가 별도로 있어야 되고, 사용자(블로그 주인)의 관리자 페이지가 별도로 있어야 한다. 시스템 관리자가 글 분류(주제)를 미리 정해 두면 일반 사용자는 글을 쓸 때 선택한다."

> 이 스펙은 두 관리 화면의 구조(진입, 권한, 메뉴, 대시보드)와 공통 규칙을 정의한다. 각 메뉴의 세부 기능은 해당 기능 스펙의 FR을 따른다(표의 "출처"). 새 요구사항은 FR-096부터다.
>
> 구현 순서: 블로그 관리의 뼈대와 001 메뉴는 001과 함께, 시스템 관리자 콘솔의 뼈대와 주제·큐레이션 메뉴는 003과 함께 만든다. 나머지 메뉴는 각 기능 스펙을 구현할 때 채운다.

## 두 관리 화면 비교

| 구분 | 시스템 관리자 콘솔 | 블로그 관리 |
|---|---|---|
| 누가 | 서비스 운영자(ADMIN 일반 관리자, SUPER_ADMIN 최고 관리자) | 모든 회원(자기 블로그만) |
| 주소 | `blog.java21.net/admin` | `blog.java21.net/{블로그주소}/manage` (`blog.java21.net/manage`는 최근에 쓴 블로그나 블로그 선택으로 이동) |
| 범위 | 서비스 전체(모든 회원, 모든 블로그, 포털) | 주소의 블로그 하나(블로그가 여럿이면 블로그마다 따로 관리) |
| 진입 | 관리자 계정 로그인 후 상단 메뉴 "시스템 관리" | 로그인 후 상단 메뉴 "내 블로그 관리" |
| 화면 | 별도 레이아웃(관리자 전용 좌측 메뉴) | 별도 레이아웃(블로그 관리 좌측 메뉴) |

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 블로그 주인이 내 블로그를 관리한다 (Priority: P1)

회원은 "내 블로그 관리"에 들어가 대시보드에서 오늘 방문자와 새 댓글을 확인하고, 좌측 메뉴에서 글·카테고리·댓글·블로그 설정을 관리한다.

**Why this priority**: 모든 회원이 매일 쓰는 화면이다. 001의 글·카테고리·댓글 관리가 여기에 모인다.

**Independent Test**: 회원으로 로그인 → "내 블로그 관리"(`/{블로그주소}/manage`) 진입 → 대시보드 수치 확인 → 글 관리에서 임시저장 글 찾기 → 카테고리 추가 → 설정에서 블로그 제목 변경 → 블로그 홈에 반영되는지 확인. 다른 회원의 블로그 관리 화면에는 들어갈 수 없는지 확인.

**Acceptance Scenarios**:

1. **Given** 로그인한 회원, **When** "내 블로그 관리"를 누르면, **Then** 자기 블로그의 관리 대시보드가 열린다. 블로그가 여러 개면 최근에 관리하거나 글을 쓴 블로그가 열리고, 알 수 없으면 블로그를 고르는 화면이 열린다.
2. **Given** 관리 대시보드, **When** 열면, **Then** 오늘·어제 방문자 수, 새 댓글·방명록(최근 7일), 최근 글 5편, 임시저장 글 수가 보인다(아직 구현되지 않은 스펙의 항목은 숨긴다. 004 전에는 글·댓글 수치만 보인다, FR-100).
3. **Given** 글 관리 메뉴(`/{블로그주소}/manage/posts`), **When** 상태(전체·발행·임시저장·휴지통, 004의 예약·005의 숨김)와 공개 범위(공개·비공개, 004의 보호)와 카테고리로 거르고 제목으로 검색하면, **Then** 조건에 맞는 내 글만 보이고 여러 글을 골라 한꺼번에 공개 범위 변경·카테고리 이동·삭제할 수 있다.
4. **Given** 댓글 관리 메뉴, **When** 열면, **Then** 내 블로그 모든 글의 댓글이 최신순으로 보이고 바로 삭제할 수 있다.
5. **Given** 다른 회원, **When** 내 블로그의 관리 화면이나 관리 API에 접근하면, **Then** 거부된다.
6. **Given** 블로그가 2개인 회원의 블로그 관리 화면, **When** 상단의 블로그 전환에서 다른 블로그를 고르면, **Then** 그 블로그의 같은 메뉴로 이동하고 글·카테고리·댓글·설정은 그 블로그의 것만 보인다.

### User Story 2 - 시스템 관리자가 서비스를 운영한다 (Priority: P2)

운영자는 "시스템 관리"에 들어가 대시보드에서 서비스 현황을 보고, 좌측 메뉴에서 주제(서비스 카테고리), 포털 추천, 회원, 신고, 서비스 설정을 관리한다.

**Why this priority**: 포털(003)의 주제와 추천, 운영(005)의 신고·정지가 모두 이 화면에서 이뤄진다.

**Independent Test**: 관리자 계정으로 `/admin` 진입 → 주제 소분류 추가 → 일반 회원 글쓰기 화면의 주제 선택에 새 소분류가 나오는지 확인. 일반 회원 계정으로 `/admin` 접근이 거부되는지 확인.

**Acceptance Scenarios**:

1. **Given** 관리자 계정, **When** "시스템 관리"를 누르면, **Then** 시스템 관리자 콘솔 대시보드가 열린다.
2. **Given** 일반 회원, **When** `/admin` 주소로 직접 들어가거나 관리자 API를 호출하면, **Then** "찾을 수 없음"과 같은 응답을 받는다(관리 화면의 존재를 드러내지 않음).
3. **Given** 콘솔 대시보드, **When** 열면, **Then** 오늘 가입자·발행 글·댓글 수, 전체 회원·블로그·글 수, 처리 대기 신고 수, 최근 7일 추이가 보인다.
4. **Given** 주제 관리 메뉴, **When** 대분류·소분류를 추가·이름 변경·순서 변경(끌어서 놓기)·숨김하면, **Then** 일반 회원의 글쓰기 화면 주제 선택과 포털 탭에 바로 반영된다.
5. **Given** 회원 관리 메뉴, **When** 이메일(전체 주소 정확히 일치만)·닉네임·블로그 주소로 회원을 찾으면, **Then** 가입일·상태·글 수·신고 받은 수가 보이고 정지·해제할 수 있다.
6. **Given** 회원 상세, **When** 관리자가 블로그 한도를 5로 정하거나 기본값으로 되돌리면, **Then** "블로그 2 / 한도 5"처럼 지금 블로그 수와 한도가 바뀌어 보이고, 그 회원은 바뀐 한도까지 블로그를 만들 수 있으며 작업 기록에 변경 전후 값이 남는다.

### User Story 3 - 관리자 작업 기록과 권한 부여 (Priority: P3)

운영자의 모든 변경 작업은 기록으로 남고, 최고 관리자는 다른 회원에게 관리자 권한을 주거나 회수한다.

**Why this priority**: 운영 사고를 추적하고 책임을 분명히 하기 위한 장치다. 운영자가 한 명일 때는 필요성이 낮다.

**Independent Test**: 관리자가 회원 정지, 주제 숨김을 수행 → 작업 기록 메뉴에 누가·언제·무엇을·어떻게 바꿨는지 2건이 남는지 확인.

**Acceptance Scenarios**:

1. **Given** 관리자, **When** 정지, 주제 변경, 추천 지정, 포털 제외, 신고 처리, 설정 변경을 하면, **Then** 작업 기록에 관리자·시각·대상·변경 전후 값이 남는다.
2. **Given** 작업 기록, **When** 관리자가 기간·관리자·작업 종류로 거르면, **Then** 해당 기록만 보인다. 기록은 수정·삭제할 수 없다.
3. **Given** 최고 관리자, **When** 회원에게 관리자 권한을 주거나 회수하면, **Then** 그 회원의 다음 요청부터 반영되고(관리자 API는 요청마다 저장된 현재 권한을 확인) 작업 기록에 남는다. 화면 상단의 "시스템 관리" 메뉴 표시는 다음 토큰 갱신 때 바뀔 수 있다.

---

### User Story 4 - 시스템 관리자가 릴리스 노트를 쓰고 게시한다 (Priority: P4)

운영자는 콘솔의 "릴리스 노트" 메뉴에서 새 버전의 릴리스 노트를 언어별로 쓰고(원고는 `blog-docs/release-notes/`의 초안을 붙여 넣는다), 게시해 포털 메인·상단 배너·`/updates`에 내보낸다(003 FR-161~166). 고칠 때마다 이전 내용이 수정본으로 남는다.

**Why this priority**: 서비스 변화를 이용자에게 알리는 수단이지만, 다른 관리 기능이 먼저 있어야 서비스가 운영된다.

**Independent Test**: 관리자가 v1.2.0을 한국어판만 넣어 초안으로 저장 → 비로그인으로 `/updates/v1.2.0`이 "찾을 수 없음"인지 확인 → 영어판을 더해 저장 → 게시 → `/updates/v1.2.0`에 보이는지 확인 → 본문을 고쳐 저장 → 수정본 목록에 3건(만들기, 영어판 추가, 게시 후 수정)이 남고 작업 기록에 만들기·수정·게시가 남는지 확인.

**Acceptance Scenarios**:

1. **Given** 관리자, **When** 버전(예: 1.2.0), 릴리스 날짜, 한국어판 제목·본문을 넣어 저장하면, **Then** 초안(DRAFT)으로 저장되고 관리자 외에게는 보이지 않는다.
2. **Given** 관리자, **When** SemVer 형식이 아닌 버전이나 이미 있는 버전을 넣거나 한국어판을 비우면, **Then** 이유와 함께 저장되지 않는다.
3. **Given** 초안, **When** 관리자가 게시하면, **Then** 게시(PUBLISHED) 상태가 되어 `/updates`와 포털 카드·회원 배너에 나온다.
4. **Given** 게시된 노트, **When** 관리자가 본문을 고쳐 저장하면, **Then** 고친 내용이 바로 보이고 이전 내용은 수정본으로 남아 관리자(수정한 관리자·시각 포함)와 독자("수정 이력")가 볼 수 있다. 버전 번호는 바꿀 수 없다.
5. **Given** 두 관리자가 같은 노트를 열어 둔 상태, **When** 한 사람이 먼저 저장한 뒤 다른 사람이 저장하면, **Then** 나중 저장은 충돌로 거부되고 최신 내용을 다시 불러오라는 안내가 나온다.
6. **Given** 관리자, **When** 노트를 만들거나 고치거나 게시·게시 중단·삭제하면, **Then** 작업 기록(FR-106)에 관리자·시각·대상 버전·변경 전후 값이 남는다.

---

### Edge Cases

- 관리자가 회원의 블로그 한도를 지금 가진 블로그 수보다 낮게(0 포함) 정해도 기존 블로그는 삭제·비공개되지 않는다. 그 회원은 블로그를 지워 한도 아래로 내려가기 전까지 새 블로그를 만들 수 없다(001 FR-158).
- 관리자도 자기 블로그를 가진 회원이므로 "내 블로그 관리"와 "시스템 관리" 두 메뉴가 모두 보인다. 두 화면은 섞이지 않는다.
- 관리자 권한이 회수된 사람이 콘솔을 열어 둔 상태라면 다음 요청부터 거부된다.
- 최고 관리자는 최소 1명이 남아야 하며 마지막 최고 관리자의 권한은 회수할 수 없다.
- 관리자가 정지된 회원의 블로그 관리 화면에 대신 들어가는 기능은 없다(콘텐츠 조치는 콘솔의 신고·포털 제외·숨김으로만).
- 관리 화면은 검색 엔진에 노출되지 않는다.
- 게시한 릴리스 노트를 게시 중단(초안으로 되돌림)하면 그 버전 주소는 독자에게 "찾을 수 없음"이 되지만 수정본과 작업 기록은 남는다. 한 번이라도 게시한 노트는 삭제할 수 없다(고유 주소와 이력 보존).
- 릴리스 노트 본문에 이미지 올리기는 1.0 범위 밖이다. 본문은 Markdown 텍스트와 링크만 쓴다.

## Requirements *(mandatory)*

### Functional Requirements

**공통**

- **FR-096**: 시스템 관리자 콘솔(`/admin`)과 블로그 관리(`/{블로그주소}/manage`, 블로그마다 따로)는 서로 다른 레이아웃·메뉴를 가진 별도 화면이어야 하며, 상단 메뉴에서 권한에 따라 각각 진입할 수 있어야 한다.
- **FR-097**: 블로그 관리는 주소의 블로그가 로그인한 회원 본인의 블로그(삭제하지 않은 것)일 때만 열리며, 다른 사람의 블로그의 관리 기능 요청은 거부해야 한다. 블로그가 여러 개인 회원은 블로그 관리 화면 상단에서 다른 블로그로 바꿀 수 있어야 하고, 상단 메뉴 "내 블로그 관리"는 최근에 관리하거나 글을 쓴 블로그(알 수 없으면 블로그 선택)로 연결한다. 시스템 관리자 콘솔은 관리자 권한(일반 관리자 ADMIN, 최고 관리자 SUPER_ADMIN)만 쓸 수 있고, 그 외 요청(비로그인 포함)에는 화면·API 모두 "찾을 수 없음"(404)으로 응답해 존재를 드러내지 않아야 한다. 관리자 권한은 요청마다 저장된 현재 권한으로 확인하며, 권한 회수는 다음 요청부터 적용된다.
- **FR-098**: 관리 화면은 검색 엔진 수집 대상에서 제외되어야 한다.

**블로그 관리 메뉴 (회원)**

- **FR-099**: 블로그 관리 메뉴는 아래로 구성하며, 아직 구현되지 않은 스펙의 메뉴는 숨긴다. 모든 메뉴의 경로는 `/{블로그주소}/manage/...`이고, 외부 블로그를 뺀 모든 메뉴는 그 블로그의 데이터만 다룬다.

  | 메뉴 | 내용 | 출처 |
  |---|---|---|
  | 대시보드 (`/{블로그주소}/manage`) | 방문자(오늘·어제), 새 댓글·방명록, 최근 글, 임시저장 수 | FR-100, 004 FR-067 |
  | 글 관리 (`/{블로그주소}/manage/posts`) | 상태(001 data-model의 status 값)·공개 범위(visibility 값)·카테고리 필터, 제목 검색, 일괄 공개 범위 변경·카테고리 이동·삭제, 휴지통(상태 필터 "휴지통")과 복구 | 001 FR-013~017, FR-084, FR-101 |
  | 카테고리 관리 | 내 블로그 카테고리(2단계) 추가·이름·순서·삭제 | 001 FR-023~024 |

- **FR-103**: 콘솔 대시보드는 오늘 가입자·발행 글·댓글 수, 전체 회원·블로그·공개 글 수, 처리 대기 신고 수, 최근 7일 일별 가입·발행 추이를 보여야 한다. 수치는 최대 5분 지연을 허용한다.
- **FR-104**: 회원 관리는 이메일(전체 주소가 정확히 일치할 때만, 부분 검색 없음, 001 FR-135)·닉네임·블로그 주소로 검색하고, 회원 상세(가입일, 상태, 글 수, 받은 신고 수, 최근 로그인 시각, 블로그 목록과 블로그 수 / 한도)를 보여야 한다. 관리자도 회원의 비밀번호나 비공개 글 본문은 볼 수 없다.
- **FR-105**: 관리자 권한은 "최고 관리자"(SUPER_ADMIN)와 "일반 관리자"(ADMIN) 두 단계이며, 관리자가 아닌 회원은 USER다(001 data-model `users.role`). 관리자 권한 부여·회수는 최고 관리자만 할 수 있고, 최고 관리자는 최소 1명 남아야 한다. 첫 최고 관리자는 서비스 설치 시 운영 설정 프로퍼티(001 contracts/api.md의 `blog.admin.bootstrap-super-admin-email`)로 지정한다.
- **FR-106**: 관리자의 모든 변경 작업(정지·해제, 주제 변경, 추천·포털 제외, 신고 처리, 콘텐츠 숨김, 설정 변경, 권한 변경, 회원별 블로그 한도 변경, 릴리스 노트 만들기·수정·게시·게시 중단·삭제)은 관리자·시각·대상·변경 전후 값으로 기록되어야 하며, 기록은 수정·삭제할 수 없고 1년간 보관한다.
- **FR-160**: 일반 관리자(ADMIN)와 최고 관리자(SUPER_ADMIN)는 회원 관리의 회원 상세에서 그 회원의 블로그 수와 현재 한도를 보고, 회원별 블로그 한도를 0 이상의 값으로 정하거나 기본값으로 되돌릴 수 있어야 한다(001 FR-158). 한도를 지금 블로그 수보다 낮춰도 기존 블로그는 그대로 두고 새로 만드는 것만 막는다. 변경은 작업 기록(FR-106)에 변경 전후 값으로 남긴다. 기본값(회원당 3개) 자체는 운영 설정 프로퍼티(001 contracts/api.md의 `blog.blogs.default-max-per-member`)로만 바꾸며, 1.0에서는 콘솔에서 바꾸지 않는다(서비스 설정 메뉴에 읽기 전용으로 표시).

**릴리스 노트**

- **FR-167**: 일반 관리자(ADMIN)와 최고 관리자(SUPER_ADMIN)는 콘솔의 "릴리스 노트" 메뉴에서 서비스 릴리스 노트를 만들고 고치고 게시할 수 있어야 한다. 노트는 버전(Semantic Versioning `MAJOR.MINOR.PATCH`, 서비스 전체에서 유일), 릴리스 날짜, 언어별 제목과 Markdown 본문을 가진다. 한국어판은 필수이고 영어·일본어·중국어(간체)판은 선택이다(독자에게는 003 FR-161의 대체 순서로 보인다). 상태는 초안(DRAFT)과 게시(PUBLISHED) 두 가지이며 게시한 노트만 회원·방문자에게 보인다. 저장 전에 독자 화면과 같은 변환 결과를 미리 볼 수 있어야 한다. 한 번 게시한 노트는 버전 번호를 바꿀 수 없고(고유 주소 유지) 삭제할 수 없으며, 게시 중단으로 초안으로 되돌릴 수만 있다. 한 번도 게시하지 않은 초안은 삭제할 수 있다. 회원과 방문자는 릴리스 노트를 읽기만 한다.
- **FR-168**: 릴리스 노트를 저장할 때마다 저장된 내용 전체(버전, 날짜, 모든 언어판)를 번호가 붙은 수정본으로 남겨야 하며, 이전 수정본은 바꾸거나 지울 수 없다(한 번도 게시하지 않은 초안을 삭제할 때만 함께 지운다). 관리자는 수정본 목록(번호, 수정한 관리자, 시각, 당시 상태)과 각 수정본 내용을 볼 수 있고, 독자는 처음 게시한 뒤의 수정본을 "수정 이력"으로 볼 수 있다(003 FR-166). 두 관리자가 같은 노트를 동시에 고치면 나중 저장이 앞 저장을 덮어쓰지 않도록 충돌로 거부해야 한다. 만들기·수정·게시·게시 중단·삭제는 작업 기록(FR-106)에 남긴다.

### Key Entities *(include if feature involves data)*

- **관리자 권한(Admin role)**: 회원의 권한 단계(USER 일반 회원 / ADMIN 일반 관리자 / SUPER_ADMIN 최고 관리자). 001의 회원 권한 값을 그대로 쓴다.
- **회원별 블로그 한도(Per-member blog limit)**: 회원이 가질 수 있는 블로그 수. 001의 `users.max_blogs`(없으면 서비스 기본값)를 쓰며 저장 테이블을 새로 두지 않는다.
- **관리자 작업 기록(Admin audit log)**: 관리자, 작업 종류, 대상 종류·ID, 변경 전·후 값, 시각, 요청 IP.
- **릴리스 노트(Release note)**: 버전(SemVer, 유일), 릴리스 날짜, 상태(초안/게시), 처음 게시 시각, 최근 게시 시각, 언어별 제목·Markdown 본문(ko 필수), 만든·마지막으로 고친 관리자. 독자 화면은 003 FR-161~166.
- **릴리스 노트 수정본(Release note revision)**: 노트, 수정본 번호, 저장 시점의 전체 내용(버전·날짜·모든 언어판), 당시 상태, 수정한 관리자, 시각. 바꾸거나 지우지 않는다.
- **예약어(Reserved handle)**: 블로그 주소로 쓸 수 없는 이름. backend 코드 상수로만 관리하며(001 contracts/routes.md), 콘솔은 읽기 전용으로 보여준다. 저장 테이블은 없다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-015**: 일반 회원 계정으로 시스템 관리자 기능에 접근이 성공한 경우가 0건이다(모든 관리자 API 권한 테스트 기준).
- **SC-016**: 회원은 "내 블로그 관리"에 들어가 원하는 글을 찾아 수정 화면까지 30초 안에 이동할 수 있다.
- **SC-017**: 관리자 변경 작업의 100%가 작업 기록에 남는다.

## Assumptions

- 두 관리 화면 모두 front 저장소 안의 화면이며 별도 앱이나 별도 도메인을 두지 않는다(헌법 원칙 II). 별도 도메인(예: admin.blog.java21.net)이 필요해지면 그때 결정한다.
- 시스템 관리자 콘솔은 데스크톱 화면 기준으로 만들고, 모바일은 조회 위주로 동작하면 된다. 블로그 관리는 모바일에서도 쓸 수 있어야 한다.
- 관리자 2단계 인증(OTP)은 이번 범위 밖이다.
- 회원당 기본 블로그 수(3개)는 운영 설정 프로퍼티이며 1.0에서는 콘솔에서 바꾸지 않는다. 바꿀 필요가 생기면 서비스 설정 메뉴에 편집 기능을 더한다.
- 001의 회원 권한 값(USER / ADMIN / SUPER_ADMIN)을 그대로 쓰며, 이 스펙은 각 권한이 쓸 수 있는 관리 기능을 정한다.
